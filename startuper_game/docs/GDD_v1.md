# Игра: "Мамкин Единорог" (GDD v1)

## 1) Концепт

- Жанр: 2D narrative-management simulator.
- Платформа: PC (Mac обязателен, Windows опционально).
- Язык: русский.
- Тон: ироничный (средний уровень), но с реалистичными продуктово-бизнесовыми последствиями.
- Длительность сессии: 20-30 минут.
- Цель: обучающая игра, которая показывает работу техстартапа через решения игрока.

Ключевая фантазия: "Я Мамкин, основатель стартапа: у меня всегда не хватает ресурсов, а любой выбор имеет цену".

## 2) Целевая аудитория и обучающие результаты

- Начинающие продакты, основатели, студенты продуктовых/предпринимательских курсов.
- Люди без опыта в стартапах, которым нужен практический симулятор.

После сессии игрок должен понимать:

- Почему нельзя оптимизировать одну метрику в отрыве от остальных.
- Как связаны `runway`, `churn`, `CAC`, скорость команды и техдолг.
- Почему важны CustDev, фокус и приоритизация.
- Зачем и когда делается пивот.

## 3) Core Loop (ядро)

Один ход = 1 игровая неделя.
Одна партия = 12 ходов (примерно 1 квартал), что укладывается в 20-30 минут.

Цикл хода:

1. Игрок получает сводку состояния (деньги, команда, метрики, риски).
2. Планирует спринт: выбирает 3-5 задач из бэклога.
3. Происходит событие недели (рыночное/командное/техническое).
4. Игра пересчитывает последствия.
5. Игрок видит обратную связь и готовится к следующей неделе.

## 4) Основные системы

### 4.1 Ресурсы

- Деньги (`cash`): основной ограничитель.
- Runway (`months_left`): сколько месяцев до нуля.
- Мораль команды (`morale`): влияет на эффективность.
- Техдолг (`tech_debt`): замедляет разработку и повышает риск инцидентов.
- Репутация (`reputation`): влияет на конверсию и найм.

### 4.2 Продуктовые метрики

- `activation` (первичная ценность).
- `retention` (удержание).
- `churn` (отток, обратная сторона retention).
- `nps` (субъективная ценность/рекомендации).
- `mrr` (ежемесячная выручка).

Важно: игра показывает причинно-следственные связи, а не только цифры.

### 4.3 Команда и роли

Стартовый состав (MVP):

- Основатель (игрок, задает приоритеты).
- Разработчик.
- Дизайнер.
- Маркетолог.

Позже можно нанимать:

- Продакт-менеджер.
- Второй разработчик.
- Сейлз (для B2B сценария).

У каждой роли есть стоимость и эффект; найм без runway может убить компанию.

### 4.4 Бэклог и приоритизация

Типы задач:

- Фичи (рост activation/revenue, часто +tech_debt).
- Исправления багов (рост retention, -репутационные риски).
- Рефакторинг (-tech_debt, но без прямого роста выручки).
- CustDev (открывает более точные гипотезы).
- Growth-эксперименты (влияют на CAC/трафик, высокий разброс результатов).

### 4.5 События (ивенты)

Ивенты короткие, с ироничным текстом и 2-3 вариантами ответа.

Примеры:

- "Инвестор просит x3 рост к следующему демо."
- "Прод внезапно лег в пятницу вечером."
- "Ключевой разработчик хочет отпуск на Бали прямо перед релизом."
- "Конкурент запустил почти вашу фичу."

У каждого варианта есть скрытая и явная цена.

## 5) Победа/поражение

### Победа (конец квартала)

- Компания жива (`cash > 0`).
- Достигнут минимальный Product-Market сигнал:
  - `retention >= 35` и `activation >= 40` (условные игровые пороги),
  - или `mrr` выше заданного порога.

### Поражение

- Деньги закончились.
- Репутация обрушилась ниже критического порога.
- Командная мораль упала до "выгорание" и скорость почти нулевая.

## 6) Прогрессия

На MVP-этапе: один сценарий "ранняя стадия стартапа".

Для полной версии:

- Сценарий A: B2C mobile.
- Сценарий B: B2B SaaS.
- Сценарий C: AI-инструмент с высокими инфраструктурными издержками.

Каждый сценарий меняет экономику и пул событий.

## 7) UX/UI (2D с персонажами)

Экраны:

- Главное меню.
- Игровой хаб (офис): персонажи и текущий статус.
- Спринт-планирование (карточки задач).
- Окно события (диалог/выбор).
- Экран метрик (графики + текстовый разбор последствий).
- Финальный экран (итоги партии + чему научился игрок).

Визуальный стиль:

- Плоская 2D-графика, выразительные персонажи, легкая карикатурность.
- Яркие акценты для рисков (красный) и положительной динамики (зеленый).

## 8) Технический выбор

Рекомендуемый движок: Godot 4.

Почему:

- Быстрый цикл итераций для UI-heavy симулятора.
- Удобный экспорт на Mac (основная платформа) и Windows (опционально).
- Простой контроль данных (ресурсы, таблицы, события).
- Легкий порог для сборки вертикального среза.

## 9) Контентный объем на версии

### Версия MVP (играбельный вертикальный срез)

- 12 ходов.
- 25-35 карточек задач.
- 20-30 событий.
- 3 концовки (успех, "на грани", провал).

### Версия 1.0

- 2-3 сценария.
- 80+ событий.
- 100+ задач/решений.
- 8-12 концовок.

## 10) Баланс (базовые формулы)

Упрощенный каркас:

- `burn_rate = salaries + infra + marketing_spend`
- `cash_next = cash_current + revenue - burn_rate`
- `runway = cash_next / max(burn_rate, 1)`
- `dev_velocity = base_velocity * morale_mod * debt_mod`
- `debt_mod = clamp(1.0 - tech_debt * 0.01, 0.5, 1.0)`
- `morale_mod = clamp(0.7 + morale * 0.006, 0.5, 1.2)`

Рост продукта зависит от качества гипотез:

- Если игрок делал CustDev, рост метрик от фич выше.
- Если игрок игнорирует баги и техдолг, шанс негативных событий повышается.

## 11) Ироничный нарратив

Принципы текста:

- Шутка есть, но данные и последствия реальные.
- Персонажи узнаваемые ("инвестор с KPI", "growth-гуру", "CTO-реалист").
- Короткие реплики, быстрый темп, без длинных стен текста.

## 12) Риски производства

- Перегрузить игру контентом без полировки core loop.
- Сделать "симулятор таблицы", где не чувствуется драма решений.
- Слишком сложные формулы для первой версии.

Антириск:

- Сначала MVP с сильной обратной связью по решениям.
- Затем наращивать контент, а не наоборот.

## 13) Definition of Done для версии 1.0

- Полный цикл 20-30 минут стабильно проходится.
- Игрок без внешних объяснений понимает причинно-следственные связи.
- Есть обучающий итог после партии (что сработало/не сработало и почему).
- Сборка на Mac стабильна.
- Минимум критических багов на сценариях успеха и провала.
